# 如何安全改进 skill（通用元规则）

改**任何自建 skill** 本身时读——不是执行 skill 任务时读。

一句话：改 skill 容易把旧功能悄悄改坏，这份规则给出一套固定流程，保证每次改动都留下测试兜底、不退化。

为什么 skill 特别容易坏？因为 skill 的产物是**规则**（一半是自然语言说明，一半是能跑的代码），规则有三个普通代码没有的毛病：

- 纯文字写的规则不会像代码那样编译报错，写错了也没人拦；
- skill 一次次进化重写，旧规则会被顺手改没、**悄无声息地丢失**（这次的题注居中、公式空格就是这么丢的）；
- 规则对不对，只能靠一条条**样例测试**去验，没有类型系统帮忙查。

所以改 skill 不能「改完就算」，要走下面这个闭环。

## 改 skill 的六步闭环

```
① 想清为什么改 ──▶ ② 把规则写扎实 ──▶ ③ 每条规则配测试 ──▶ ④ 别走捷径糊弄
   ▲                                                          │
   └────── ⑥ 验收 + 把教训存回来 ◀── ⑤ 守住边界、想好取舍 ◀───┘
```

每次改 skill 从 ① 走到 ⑥，跳过哪步，坑就留在哪步。每步末尾都有一句「做到这样才算过」。

---

## ① 想清为什么改

- 改动要么是为了**用户能看到的效果**，要么是**修一个已经发生的退化**。答不出改了带来啥效果，就是为改而改，停手。
- 如果是修退化，先搞清根子出在哪，对上下面的病根表。说不清踩了哪个坑，多半是还没查清。

**三种反复发生的坑**（改规则前先拿这三条照一照自己）：

| 坑 | 长什么样 |
|------|------|
| **规则太死** | 只盯着一个样例总结规则，规则贴死表面特征，换一类输入就错 |
| **修一个碰坏另一个** | 修 A 时改了共用的规则/正则，没回头验 B 还对不对 |
| **规则只写在文档里，没配测试** | 文档郑重写了「必须怎样」，但没有对应测试；skill 下次重写时它就没了，CI 也不会报警 |

**做到这样才算过：** 能一句话说清「这次改是为了哪个效果 / 修哪次退化」，并指出踩的是哪个坑。

---

## ② 把规则写扎实（闸 1：能不能扛住换输入）

一条规则要经得起「换一类输入还对吗」。下面任一条答「否」，就说明规则还没写好：

1. **样例够不够杂？** 至少覆盖多类：中文、英文、数字、标点、全角/半角、大小写。
2. **讲清了机制还是只描述了现象？** 要写清背后的标准、渲染器行为或 DOM 结构；只会复述当前样例不够。
3. **有反例吗？** 每条检测规则至少配 2 个「本不该命中」的样例，防止误伤和过度修复。
4. **字符范围划准了吗？** 涉及边界时分清字母、数字、CJK、标点、空白；`\S`、`.`、`\w` 这类大范围先当嫌疑犯。
5. **标了平台差异吗？** GitHub、VS Code、KaTeX、MathJax 行为不同时，必须写清这条规则管哪个平台。

**做到这样才算过：** 多类正例 + 每条规则 ≥2 反例，机制写清，平台标明。

---

## ③ 每条规则配测试（闸 2 铁律）

skill 有两拨读者——**用户看的是效果，机器执行的是合同**。两边都要落地，少一边规则就会飘掉。

### 给机器的：闸 2 铁律

**凡是写进文档的效果规则（必须 / 默认 / 守恒 / 居中 / 边界这类），同一个 PR 里必须同时交出对应的 CI 测试。** 只有文档、没有测试的规则，一律当**没做完，不许合并**。这是硬门槛，不是「最好有」。

自查一句：

> 这条规则要是被删了，哪个测试会变红？答不上来，就是还没配测试——补上再合并。

- 各 skill 的专属样例登记在它自己的 `self-improvement.md`；但**登记了不等于配了测试**，登记表里每条机器能判的规则都要有 `tests/` 里的测试兜底。
- 改规则时跑**完整测试集**（全部测试），不是只跑刚加的那几个。
- 老样例原则上不删；确实被证明是错的，写下原因再改。
- 文档里的 selector、正则、默认行为，如果有能跑的实现，**以实现和测试为准**（文档描述过时时听代码的）。

跑测试：

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests -p 'test_*.py' -v
```

GitHub Actions 会在提 PR 和推 `main` 时跑同一套。

### 给用户的：验收清单（用户唯一要碰的文件）

用户只描述**想要的效果**，不碰实现（正则、selector、路由）。把效果翻译成机器能判的测试，是 Claude 的活，不是用户的。

- 每个 skill 存一份 `<skill>/acceptance/CASES.md`：纯中文效果清单，一条写「想要什么效果 → 用哪个样例 → 期望结果 → 什么情况不该触发」。
- 每条都要有对应的 `tests/test_acceptance_*.py`，清单条目末尾标上测试名，用户一眼能确认「这条有机器盯着」。
- 用户加一条中文效果 → Claude 找/造真实样例 → 写成端到端测试 → 把测试名填回清单。
- CASES.md 就是闸 2 铁律的「用户友好入口」：用户看得懂的效果进 CASES.md，看不懂的内部机制规则照样各自配测试。

**做到这样才算过：** 这次涉及的每条效果规则，机器这边有测试、用户看得懂的那条进了 CASES.md 并填了测试名。

> 以后可以加个自动检查（仿照 `test_documentation_alignment`）扫一遍 CASES.md，哪条没配测试就亮红灯。这个检查还没做之前，先靠本步的约定 + 铁律顶着。

---

## ④ 别走捷径糊弄（踩任一条就算没做完）

测试变绿 ≠ 功能真对。下面这些捷径让绿灯盖住了破坏，比不改还危险：

- **把正则改宽 / 把断言放松，让测试过** —— 而不是把逻辑改对。测试是用来钉住效果的，不是用来凑绿的。
- **只跑新加的测试，不跑全部** —— 会漏掉对老场景的连带破坏（就是「修一个碰坏另一个」）。
- **删掉或改掉老测试，把红改绿** —— 除非那个场景确实被证明错了并写了原因，否则不许。
- **文档改了，假装配了测试** —— 就是「规则只写文档没配测试」这个坑。答不出「删了它哪个测试会红」，就是没配。
- **手写一份假的 `converted` / 成功报告，绕过 `blocked`** —— 卡在 `blocked` 就得真修好再重跑，不许伪造报告。
- **用 `textContent` 假装公式/结构提取成功了** —— 提取失败就得 fail-closed（保守停下）上报或转人工，不许把错误吞掉装成功。
- **用时间戳/随机数/hash 去凑唯一名、消重名** —— 命名和判定必须确定、可重复。

**做到这样才算过：** 逐条对照，一条都没踩。

---

## ⑤ 守住边界、想好取舍、留好后路

**边界（能碰什么）：** 只改跟这次目的直接相关的规则/代码。别顺手重构无关模块，别删改老测试（除非那场景被证明错了并记原因）。skill 的规则常被多处共用，越界改一条正则，可能同时崩三个 skill。

**取舍（冲突时保什么）：** 按这个优先级排——

> **fail-closed（宁可保守停下）＞ 结果可重复 ＞ 结构不丢（表格/公式/列表数量守恒）＞ 覆盖更多情况 ＞ 写得简洁**

速度不在这个排序里：快慢靠 fast/strict 分流解决，不靠牺牲正确性去换。要动高优先级的项，必须说清楚并让用户点头。

**留好后路（碰到没预料的情况）：** fail-closed——保守处理：路由到 strict、保留原始、或直接卡住（`blocked`），记下来并上报。绝不猜一把然后假装成功放过去。这是 skill 遇到没见过的页面结构时的默认姿态。

**做到这样才算过：** 改动没超出目的范围；冲突按优先级裁决并记录；没预料的情况一律保守处理 + 上报。

---

## ⑥ 验收 + 把教训存回来

- 跑全部测试 + CI 全绿；语义和视觉类规则还要人工验：数量对不对、渲染对不对、截图对不对（列表符号、公式结构、图片完整性、渲染截图、站点专属处理，这些机器判不了，得人看）。
- 全仓搜一遍同一个 selector、正则、默认行为，把冲突的旧副本清掉。
- PR 描述写清四件事：根子在哪、有什么风险、怎么验的、哪些还没覆盖。
- 这轮新发现的退化 / 新学到的捷径 → **反过来补进** ① 的病根表或 ④ 的捷径清单，下轮一开始就能照到。这一步让闭环真正闭上，规则库越用越结实。

**做到这样才算过：** 全绿 + 人工验过 + 没有冲突副本 + PR 说清四件事 + 新教训已经补回清单。

---

**通用教训：** 边界和特殊符号规则对不对，取决于字符范围划得准不准。范围划粗了，修复动作本身就会变成下一个 bug。
